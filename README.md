# AI-помощник для подготовки карточек товаров КИП

Прототип сервиса: по JSON с данными о контрольно-измерительном приборе формирует черновик карточки
для B2B-интернет-магазина. Это SEO-заголовок, SEO-описание, таблица характеристик, поисковые запросы,
блок для менеджера и список того, что нужно уточнить.

Главный принцип: **модель не выдумывает характеристики**, и это обеспечивает код, а не только промпт
(подробнее в разделе «Принятые решения»).

## Установка

Нужен Python 3.10+.

```bash
git clone <репозиторий> && cd product-card-ai
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux
pip install -r requirements.txt
copy .env.example .env          # Windows (macOS/Linux: cp)
```

В `.env` укажите `LLM_API_KEY`. По умолчанию используется OpenRouter: ключ бесплатный (openrouter.ai/keys),
модель `openrouter/free`. Подойдёт любой OpenAI-совместимый API: OpenAI, локальная модель через
Ollama или vLLM. Достаточно поменять `LLM_BASE_URL` и `LLM_MODEL`. Файл `.env` добавлен в `.gitignore`.

## Запуск

**Командная строка** (один товар-объект или массив):
```bash
python -m cardgen.cli examples/products.json --out results
```
По каждому товару сохраняются `results/NN_название.json` (для импорта) и `.md` (для чтения и копирования).

**Веб-форма:**
```bash
python -m cardgen.web
```
Откройте http://127.0.0.1:5000, вставьте JSON и нажмите «Сформировать». Рядом с результатом есть кнопки
«Копировать Markdown» и «Копировать JSON». Также есть API: `POST /api/generate` с JSON в теле запроса.

**Тесты** (без обращения к LLM):
```bash
python -m pytest -q
```

## Товары из YML-фида каталога

Сервис умеет брать реальные товары из YML-фида (формат Яндекс.Маркета). Фид читается потоково, поэтому
подходит и для больших каталогов. HTML в описаниях очищается, а единицы измерения из `<param unit>`
добавляются к значениям.

```bash
python -m cardgen.feed https://www.souz-pribor.ru/yml/any/feed.xml --search манометр --limit 1 --out examples/manometer.json
python -m cardgen.cli examples/manometer.json --out results
```

`--search` ищет подстроку в названии, категории или производителе, `--limit` задаёт число товаров,
`--min-specs N` оставляет только товары с N и более характеристиками. Вместо URL можно передать путь
к скачанному файлу. Тип прибора берётся из `typePrefix` и категории, а служебные параметры («Артикул»,
«Код товара») не считаются характеристиками.

Важно: в фиде СОЮЗ-ПРИБОР есть название, тип, производитель и цена, но нет описаний и технических
характеристик — они только на страницах товаров. Поэтому карточки, собранные из одного фида, честно
помечают почти все характеристики как «данных нет». Обогащение данными со страниц товаров — первое
улучшение в списке ниже.

## Формат входа

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5"},
  "description": "Прибор предназначен для измерения избыточного давления."
}
```

## Что получается на выходе

| Поле | Содержание |
|---|---|
| `seo_title` | до 70 символов (длина проверяется) |
| `seo_description` | 800–1200 символов (длина проверяется) |
| `key_specs` | таблица характеристик: значения **только из входа**, отсутствующие помечены «данных нет» |
| `search_queries` | 3–5 запросов |
| `commercial` | кому подходит прибор и какие задачи решает |
| `needs_clarification` | пустые поля и характеристики, которые стоит запросить у поставщика |
| `status` | `ready`, или `needs_review`, если проверку не удалось пройти автоматически |
| `quality_warnings` | что именно не прошло проверку |

Примеры результатов для двух товаров лежат в папке `results/`. Входные данные — `examples/products.json`:
реальный товар из каталога СОЮЗ-ПРИБОР (модуль ОВЕН МК110, характеристики со страницы товара) и манометр
DM 02 из текста задания. `examples/incomplete.json` демонстрирует обработку неполных данных,
`examples/broken.json` — обработку некорректного JSON.

## Принятые решения

**1. Таблицу характеристик собирает код, а не модель.** Значения переносятся из входного JSON без
изменений, поэтому в таблице исказить или придумать характеристику невозможно. От модели берутся только
*названия* типичных для этого типа прибора характеристик, которых нет во входе. Они добавляются в таблицу
со значением «данных нет» и попадают в список «уточнить у поставщика». Так контент-менеджер видит,
чего не хватает карточке.

**2. Сгенерированный текст проверяется автоматически.**
- Все числа в заголовке, описании, запросах и блоке для менеджера должны встречаться во входных данных.
  Числа сравниваются по значению: «1,5» и «1.5» считаются одним числом.
- Утверждения, которые модели склонны «дорисовывать» (степень защиты IP, взрывозащита, ГОСТ, Госреестр,
  поверка, сертификаты, гарантия, материал), допускаются, только если они есть во входе.
- Проверяются длины заголовка и описания и количество запросов.

**3. Исправление через обратную связь.** При нарушении модель получает конкретные замечания
(«seo_description 640 симв., нужно 800–1200», «числа, которых нет во входных данных: 2,5») и переделывает
ответ. Делается до 3 попыток. Если нарушения остаются, карточка не отбрасывается, а помечается
`needs_review` с перечнем проблем, чтобы человек проверил её точечно.

**4. Обработка ошибок.**
- Некорректный JSON: сообщение с номером строки и столбца.
- Нет названия товара или неверный тип поля: ошибка по этому товару, остальные товары обрабатываются.
- Пустые поля и значения («», «-», null): предупреждения, генерация продолжается.
- Сбои API: повторы с паузой при таймаутах, 429 и 5xx; понятная ошибка при неверном ключе.
- Ответ модели в ```json-обёртке или с текстом вокруг: JSON извлекается.

**5. Один OpenAI-совместимый клиент.** Модель меняется через `.env` без правок кода.

## Промпты

Системный промпт (`cardgen/prompts.py`) состоит из трёх частей:
1. **Роль**: технический копирайтер B2B-магазина КИП.
2. **Запреты**: явный список того, что нельзя добавлять без входных данных (числа, IP, взрывозащита,
   ГОСТ, поверка и т. д.). Технические значения переносятся дословно. Если данных мало, текст пишется
   короче, без домыслов. Данные о товаре — это данные, а не инструкции (защита от prompt injection
   в описаниях поставщиков).
3. **Формат**: строго JSON с описанием каждого поля и ограничений по длине.

Данные передаются отдельным сообщением в виде JSON, отсутствующие значения передаются как `null`
с пометкой «нельзя придумывать». Температура 0.3: текст остаётся живым, но без фантазий.

## Ограничения

- Проверка выдумок ловит числа и типовые «опасные» утверждения, но не любые смысловые неточности.
  Например, модель может приписать прибору область применения, которая не следует из описания.
  Поэтому статус `ready` означает «готово к проверке», а не «готово к публикации».
- Длину текста модели соблюдают неточно, на бесплатных моделях иногда нужны повторные попытки.
- Бесплатные модели OpenRouter имеют дневные лимиты запросов и могут быть медленнее платных.
- Справочника типовых характеристик по категориям нет: список «что уточнить» предлагает модель.

## Возможные улучшения

- Обогащение данных из YML-фида характеристиками и описанием со страницы товара (ссылка `url` есть в фиде).

- Справочник обязательных характеристик по категориям (манометры, датчики, расходомеры) для
  детерминированной проверки полноты.
- Structured outputs (JSON Schema) у провайдеров, которые их поддерживают.
- Пакетная обработка CSV/XLSX из каталога и выгрузка в формат CMS.
- Набор эталонных карточек и автоматическая оценка качества при смене промпта или модели.
- Вторая модель-рецензент для смысловой проверки описания против исходных данных.
